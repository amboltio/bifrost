description: "Provision local superadmins from the gateway terminal and sign in with individual accounts."

A fresh gateway keeps dashboard management closed until an administrator exists. The login page shows terminal provisioning instructions, and `GET /api/session/is-auth-enabled` reports `admin_provisioning_required: true`. Health and public authentication status endpoints remain reachable. Inference authorization is controlled separately by `enforce_auth_on_inference` and your inference credentials.

## Create a superadmin

Run the gateway binary against the **same app directory, config store and encryption configuration as the running gateway**. This command opens the configured SQLite or PostgreSQL store without starting an HTTP server or provider integrations:

```bash
./bifrost-http createsuperadmin --app-dir /path/to/data
```

Enter an email address, display name and a strong password when prompted. Password entry is hidden and requires confirmation. The password is stored as an Argon2id verifier.

For a Docker deployment, enter the running container's terminal:

```bash
docker exec -it <gateway-container> /app/main createsuperadmin --app-dir /app/data
```

In **Coolify**, open the Bifrost service's **Terminal** and run:

```bash
/app/main createsuperadmin --app-dir /app/data
```

Use your deployment's actual `--app-dir` if it differs from `/app/data`. The directory must contain the same `config.json` and persistent SQLite files, or select the same PostgreSQL database. Run from the gateway's working directory: an explicitly configured relative SQLite path is resolved against that directory. Docker's default container working directory already matches the running gateway. Keep the existing encryption key and any environment or secret references available to the command. Do not run it against an empty replacement directory or a different database.

Automation can supply the password through standard input. Obtain it from your secret manager; do not put it in command-line arguments, shell history or logs:

```bash
read -r -s -p 'New administrator password: ' BIFROST_NEW_PASSWORD; echo
printf '%s\n' "$BIFROST_NEW_PASSWORD" | docker exec -i <gateway-container> \
  /app/main createsuperadmin --app-dir /app/data \
  --email operator@example.com --display-name 'Gateway Operator' --password-stdin
unset BIFROST_NEW_PASSWORD
```

## Sign in and manage users

Open the gateway URL and sign in with the new email address and password. Creating an administrator on a running empty gateway permits normal login without a restart. Authenticated sessions use the HTTPOnly session cookie; API clients can use the session token issued by canonical login as an `Authorization: Bearer <session>` credential. Shared legacy passwords, HTTP Basic credentials and base64 username/password Bearer values do not grant canonical management access.

Manage individual accounts, passwords and role grants under **Workspace → Governance → Users**. Configure local sign-in and session limits under login access settings. Existing OIDC providers and other login policy settings are retained when the CLI enables local sign-in for the new administrator.

## Additional administrators and access recovery

Run `createsuperadmin` again with a **different email address** to add another active superadmin. The command works on initialized databases and preserves existing users, role grants, sessions and virtual keys. A duplicate email fails without changing the existing user, password, activation state or permissions. It never resets, reactivates or promotes an existing identity. To recover access, create a distinct superadmin, sign in normally and manage the original account through Users.

Existing legacy credential migration remains for upgrades of established installations. New installations and recovery use this terminal command. No browser or HTTP endpoint provisions the initial administrator.
